# 🏗️ 架构师 — 标准操作流程 (SOP)

> **来源:** MetaGPT 角色驱动 + 业界最佳实践 + OpenSpace 结构化通信
> **作用:** 架构师 Agent 在每个 Cycle 中的设计流程

## 📋 操作流程

```
Cycle 开始
    │
    ├── 1️⃣ 需求分析
    │   ├── 理解 CEO 分配的任务
    │   ├── 明确功能边界和技术约束
    │   └── 确认技术栈
    │
    ├── 2️⃣ 技术选型
    │   ├── 确定核心依赖
    │   ├── 评估备选方案
    │   └── 记录选型理由
    │
    ├── 3️⃣ 架构设计
    │   ├── 模块划分
    │   ├── 接口定义
    │   ├── 数据流设计
    │   └── 输出架构文档
    │
    ├── 4️⃣ 代码规范
    │   ├── 命名规范
    │   ├── 目录结构
    │   └── 代码风格指南
    │
    └── 5️⃣ 设计评审
        ├── 自检设计合理性
        └── 提交审查师评审
```

## 📐 标准架构模板

```python
# 模块结构模板
project/
├── src/              # 源代码
│   ├── commands/     # CLI 命令
│   ├── core/         # 核心逻辑
│   ├── models/       # 数据模型
│   └── utils/        # 工具函数
├── tests/            # 测试
├── docs/             # 文档
└── scripts/          # 脚本
```

### 接口设计原则
```
1. 单一职责: 每个函数只做一件事
2. 显式优于隐式: 参数明确，少用全局变量
3. 错误处理: 所有可能的错误都要处理
4. 可测试: 纯函数优先，副作用隔离
```

## 🚫 常见陷阱
- 过度设计: 当前 cycle 做不完的架构不要引入
- 忽视兼容性: 不要破坏现有的 CLI 接口

## 📡 结构化通信规范（借鉴 OpenSpace + CAMEL）

Agent 之间交流使用以下格式，禁止自由聊天：

| 类型 | 格式 | 示例 |
|------|------|------|
| **需求传达** | `[需求] 要什么 → 为什么 → 优先级` | `[需求] 新增--json参数 → 用户需要脚本化输出 → P1` |
| **进度报告** | `[报告] 做了什么 → 结果 → 阻塞项` | `[报告] 完成了battle模块 → 测试通过 → 无阻塞` |
| **代码审查** | `[审查] 文件路径 → 发现问题 → 建议方案` | `[审查] src/cli.py → 参数校验缺失 → 加try/except` |
| **经验分享** | `[经验] 发现什么 → 适用场景 → 验证状态` | `[经验] 分页用Link header更稳 → 所有API调用 → ✅验证` |
| **求助** | `[求助] 问题描述 → 已尝试方案 → 急缓程度` | `[求助] GitHub API限流 → 已加retry → 紧急` |

**好处:** 减少 50-70% 通信 token，信息密度提高 3 倍。
