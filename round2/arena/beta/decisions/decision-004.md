## 差距分析

1. 体验面：README 和 npm 上线叙事仍是我们的优势位，对手在补文案但还没形成“已发布 + 可直接用”的心智。
2. 可靠性面：我们现在最大的短板不是功能，而是发布入口的验证链断了——CLI 集成测试直接指向未构建产物，导致全量测试不绿。
3. 对手动向：Alpha 在补 `read` 命令，会拉高功能完整度；但他们还没展示“可安装即用”的渠道优势。我们该把“build → CLI → npm”这条链打实。
4. 节奏面：本 cycle 最值钱的是 2-3 个小而硬的提交，不是开大功能。commit 必须继续保持小而准。

---

## 策略

**核心策略：70% 修我方发布可靠性，30% 用体验文案放大优势。**

本轮不开新命令，优先修三件事：
- 让 CLI 构建产物测试可重复通过
- 给测试面补一层“build/package smoke”防回归
- 把 README 的 npm/体验卖点与真实现状对齐，避免空喊

为什么这样打：
- 当前阻塞分数的是红测，不是缺想法。
- `cli.test.ts` 暴露的是上线链路问题，修好后能同时提升“可发布性 + 质量”两项。
- Alpha 刚补 `read`，说明他们在拉功能数；我们反而要把“装上就能跑、看起来更顺手”钉死。

## 分配

### Task 004 (P0) — 修复 CLI 构建测试链
[需求] 要什么→让 `tests/cli.test.ts` 不再依赖缺失的 `dist/cli.js`，建立稳定的构建前置或测试内自举→为什么：当前全量测试唯一红点就在这里→优先级：P0

### Task 005 (P1) — 增加发布 smoke test
[需求] 要什么→补一个极小测试，覆盖 `npm pack`/构建产物存在/二进制入口映射之一，确保以后不是只测源码→为什么：我们的差异化是“先发上线”，那就得把发布链测住→优先级：P1

### Task 006 (P2) — README 对齐真实可发布状态
[需求] 要什么→基于当前 package 版本 `0.1.0` 与已有能力，收紧 README 里的发布叙事和 CTA，强调 chalk 卡片、Markdown 导出、订阅方向→为什么：对手在补 release messaging，我们要继续赢第一印象，但不能写超前承诺→优先级：P2

## 复盘

[经验] 发现→当前最贵的不是缺功能，而是“发布入口不可验证”→场景：npm 型 CLI 项目、对手开始补命令数时→验证：本地全量测试仅 `cli.test.ts` 因缺 `dist/cli.js` 失败，其他 40 tests 通过

一句话：这轮不跟 Alpha 比命令数，先把“能 build、能跑、能测、能发”的链路钉牢，再用体验文案把这条护城河讲清楚。
